4. 이번 구현과 구현하지 않은 것
추가 소스: Assets/Scripts/Server/PopupStoreWalletCutover.cs
추가 검사: Assets/Editor/PandaRestaurant/StaffDataValidation/PopupStoreWalletCutoverTests.cs
두 파일의 .meta도 신규다. 다른 경제/게임/UI 파일 수정 없음.

구현한 순수 서버 이전 계획:
- 인증된 계정별 단일 journal: Frozen -> ImportPending -> DatabaseOnly
- 전송 결과 불명: RecoveryRequired. 재접속 후 동일 ImportKey 조회로만 복구
- 최초 freeze는 계정 고유 Insert, 이후 상태는 ExpectedRevision 조건부 Update가 필수
- 서버에서 읽은 동결 원본 행 ID, SHA-256 digest, 잔액을 고정. 클라이언트 UserInfo 잔액을 import하지 않음
- 임시 로컬 저장 잠금이 아니라 서버 전체 legacy write fence + 진행 중 요청 drain + 12개 경로 이전 증거 요구
- 원본이 바뀌면 잔액을 재기준화하거나 새 요청으로 대체하지 않고 차단
- import는 같은 Database의 신규 지갑/고유 이전 영수증을 원자적으로 삽입해야 함
- 활성화는 정확히 같은 계정/지갑/이전ID/ImportKey/원본/초기버전0/거래ID가 있는 영수증 조회 후만 가능
- 기존 활성 상태 재확인은 무변경. 오래된 이전 영수증 잔액을 최신 잔액에 다시 적용하지 않음
- 전환 후 서버 fence/경로 증거가 취소되면 신규 원장도 잠금. 이전 GameData writer를 되살리는 자동 rollback 없음
- 모든 상태가 legacy Dia 쓰기를 거절하는 정책 제공. 실제 기존 호출자 연결은 이번에 하지 않음

중요한 제한:
IWalletCutoverHostProofs의 실제 구현은 제공하지 않았다. 기본 null은 모두 차단한다.
테스트 fake의 true 값은 서버 권한/원자성/구버전 차단이 현실에서 완료됐다는 증거가 아니다.
WalletCutoverTransition은 순수 계획이다. 실제 영속 저장 성공 전 After 상태를 활성 상태로 사용하면 안 된다.
WalletCutoverRecord.CanUseDatabaseWallet은 상태/ID 확인만 한다. 실제 host는 coordinator의 같은 이름 메서드로
현재 서버 증거까지 확인하고, 그 후 기존 claim guard/fresh QUERY/인증 epoch 검증을 계속 사용해야 한다.
구버전 모든 writer 차단, 각 상품의 결제·지급 동시 거래, 원본 export, 데이터 이전 자체는 NOT RUN이다.
단순 AddDia + AsyncSave 동기화, 양쪽 잔액 중 큰 값 선택, 중복 import 금지.

6. 안전한 후속 이전 순서 (이번 차수에 실행하지 않음)
1) 별도 개발 프로젝트 + 테스트 계정 2개와 2기기. 운영 계정/키를 복사하지 않는다.
2) B 지갑 계약/모든 writer 목록을 승인한다. 소비는 비용뿐 아니라 상품 지급도 같은 권한 거래로 옮긴다.
   가챠·상점 상품이 GameData에 남으면 cross-store 원자성 문제가 그대로이므로 상품 원장 이전 또는
   서버 예약/정산 프로토콜을 먼저 완성하고, 두 저장소 간 원자성으로 부르지 않는다.
3) 구버전은 서버에서 차단하거나 새 서버 경로만 사용하는 검증된 호환 gateway 제공. 클라이언트 버전 if문만 금지.
   GameData 전체 행에 Dia와 다른 데이터가 섞여 있으므로 Dia만 필드 권한으로 차단된다고 가정하지 않는다.
   서버 함수 gateway로 모든 해당 행 write를 이동하거나 검증된 서버 권한 정책 없으면 cutover 중단.
4) 대상 계정의 모든 옛 요청 drain 및 durable fence를 검증한 뒤 서버 원본 export/digest/잔액 대조.
   export 범위, 접근 권한, 암호화 보관·보유기간·복구 책임자는 운영 승인 필요. 이번에 임의 백업 안 함.
5) 고유 migration journal 기록 -> import intent 영속화 -> 신규 wallet + unique receipt 원자 Insert.
   기존 wallet이 있으면 덮어쓰지 않는다. 다른 migration/wallet/source면 조사 후 수동 처리.
6) 응답 유실은 같은 ImportKey 조회. 불명/없음 응답만으로 새 import를 허용하지 않는다.
7) 모든 경로/원본/영수증 재확인 후 DatabaseOnly. GameData.Dia는 읽기 전용 역사자료로 남긴다.
8) 클라이언트 로딩/자동저장에서 Dia 쓰기를 제거하고 서버 최신 version 조회로만 화면을 동기화한다.
   역사 claim/import 금액을 더하거나 과거 스냅샷으로 덮어쓰지 않는다.
9) 재접속·두 기기·계정 A/B/A·동시 가챠/지급·광고/IAP/우편 지연·원장 장애·구버전 요청 검증.
10) 운영 전 승인: 환경 확인, 잔액 검증 보고, 모든 writer 제거, 키/권한/최소버전, 사고 복구 절차,
    실제 SDK 빌드/개발서버 거래 결과. 운영으로 이동하려면 별도 배포 승인 필요.

복구/rollback:
- DatabaseOnly 뒤에는 GameData.Dia를 다시 권한으로 활성화하지 않는다.
- 장애 시 양쪽 쓰기를 동결하고, 원래 import receipt와 이후 Database 거래원장을 대조한다.
- 손상/복구 판단은 서버 관리자 승인 후 보상 거래로 수행한다. 원장 삭제·잔액 두 번 import 금지.
- 클라이언트 캐시는 폐기 가능한 화면 자료다. 서버 미확정 거래는 durable journal로 먼저 복구한다.
